# Maestro Workspace Guidance

Start here:
- Read `doc/WORKFLOW_RULES.md` first.
- Use `./scripts/maestro ...` from the project root.
- Treat `.maestro/*` as the workflow truth source.
- Treat `execState` as the only lifecycle truth; `ownerRole`, `gateProfile`, board placement, and next-step hints are derived companions.

Core rules:
- Follow the active chains: `sage -> dev -> qa -> sage(close)` and `sage -> design -> sage(close)`.
- Do not edit `tasks.json` or `project.json` directly.
- Do not hand off a task unless the next role can execute it immediately.
- Normal path should auto-advance to the current role boundary.
- Only interrupt the user on failure, conflict, blockage, or unclear spec.
- In abnormal situations, Sage may use `./scripts/maestro transition force ...` only after the user explicitly authorizes the override.

Framework position:
- Maestro is a vendor-neutral workflow framework; the AI platform supplies the worker and Maestro supplies the shared workflow contract.
- This repository currently uses the `software-development` profile.
- Generated guidance is a translation layer and must not contradict `task context`, `SPEC`, `README_AGENT`, or `WORKFLOW_RULES`.

Task execution:
- Read `maestro task context <TASK-ID> --role <role>` before acting.
- Prefer JSON interfaces for machine consumption:
  - `maestro task context <TASK-ID> --role <role> --json`
  - `maestro task status <TASK-ID> --json`
  - `maestro gate run <TASK-ID> --role <role> --json`
- Long markdown details should use `--details-file` or `--details-stdin`.

Platform note:
- This file is generated by Maestro.
- Shared workflow rules remain in `doc/README_AGENT.md`, `doc/WORKFLOW_RULES.md`, and `.maestro/agent_core_template.json`.
- Repository skills are generated into `.codex/skills/`.
- In linked worktrees, CLI and App still read the primary project root `.maestro/`.
- Use role-appropriate skills when relevant:
  - `sage-task-publish-review`
  - `dev-systematic-debugging`
  - `design-ui-shell`
  - `qa-verification-before-close`
- After Sage publishes a task, push if the current project has a working Git repository and remote; QA depends on code diff visibility.
- In `closing`, Sage performs final review and may formally roll the task back to `qa` or `in_progress` if close conditions are not met.
